# Описание API и внешних сервисов

Этот документ детализирует, как "Мульти-Ассистент" взаимодействует с внешними API языковых моделей (LLM), такими как OpenAI и Google Gemini.

## 1. Провайдер Языковых Моделей (`llm_provider.py`)

Центральным элементом архитектуры взаимодействия с AI является `llm_provider.py`. Он выполняет роль **абстрактной фабрики**, которая предоставляет унифицированный способ получения ответов от разных LLM, скрывая детали их реализации от обработчиков (`handlers`).

### Ключевые функции:

-   **`set_active_llm(model_name: str, user_id: int | None = None)`**: Устанавливает, какую модель использовать.
    -   Если `user_id` указан, выбор сохраняется **персонально для этого пользователя**.
    -   Если `user_id` не указан, выбор применяется **глобально** для всех пользователей, у которых нет персональных настроек.

-   **`get_llm_answer(user_id: int | None = None)`**: Возвращает функцию-клиент для получения ответа от модели.
    -   Приоритет отдается персональной настройке пользователя.
    -   Если ее нет, используется глобальная настройка.
    -   Если глобальная настройка не задана, используется модель по умолчанию из `.env` (`DEFAULT_LLM`).

Такой подход позволяет легко добавлять новые LLM-провайдеры в будущем, не изменяя код в обработчиках.

## 2. "Строители" запросов (`*_service_build.py`)

Перед отправкой запроса к LLM его необходимо правильно сформировать. За эту задачу отвечают "строители" (builders), находящиеся в:
-   `app/services/gpt_service/chat_gpt_service_build.py` (для OpenAI)
-   `app/services/gemini_service/gemini_service_build.py` (для Gemini)

### Принцип работы:

Каждый режим работы бота (`random_fact`, `chat`, `persona`, `quiz` и т.д.) имеет свою функцию-строитель. Эта функция принимает на вход:
-   **`preset`**: Словарь из `dict_preset.py` с базовыми инструкциями (`developer`, `system`).
-   **`user_text`**: Текст, введенный пользователем.
-   **`**kw`**: Дополнительные именованные аргументы, специфичные для режима (например, `role_hint` для `persona` или `topic` и `difficulty` для `quiz`).

Задача строителя — собрать из этих данных полезную нагрузку (`payload`) в формате, который ожидает конкретное API (OpenAI или Gemini).

### Пример для режима `quiz`:

-   **Входные данные**: тема "Наука", сложность "hard", история предыдущих вопросов.
-   **Логика строителя**:
    1.  Берет базовый `developer` промпт из пресета.
    2.  Добавляет к нему динамические инструкции: `"...по теме Наука и сложности hard."`
    3.  Внедряет список уже заданных вопросов с указанием **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО повторять**.
    4.  Добавляет требование к формату ответа (строго JSON).
-   **Результат**: Готовый, сложный системный промпт, который максимизирует шансы на получение корректного и уникального вопроса от LLM.

## 3. Особенности работы с API

### OpenAI (`gpt_service`)

-   **Формат сообщений**: Использует структуру со словарями, где каждое сообщение имеет `role` (`system`, `developer`, `user`, `assistant`) и `content`.
-   **Контекст чата**: В режиме `chat` история диалога передается в виде списка предыдущих сообщений.

### Google Gemini (`gemini_service`)

-   **Формат сообщений**: Имеет схожую, но немного отличающуюся структуру. `system_instruction` передается отдельно от основного контента (`contents`).
-   **Контекст чата**: История также преобразуется в специальный формат, ожидаемый Gemini API.
-   **Обработка ошибок**: Клиент Gemini имеет свою специфику обработки ошибок, которая обернута в `try...except` блок в `gemini_service.py`.

### Парсинг JSON (`json_sanitizer.py`)

Оба API могут "заворачивать" JSON-ответы в Markdown-блоки (```json ... ```) или добавлять пояснительный текст. Сервис **`extract_json_str`** отвечает за надежное извлечение чистой JSON-строки из ответа модели перед ее парсингом, что делает модули `quiz_service` и `recommendation_service` более устойчивыми к изменениям в поведении LLM.
